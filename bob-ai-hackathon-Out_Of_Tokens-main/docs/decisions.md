Running log of tradeoff calls made during development.
Add a line the moment a decision is made — takes 30 seconds and prevents scrambling during the pitch.

## 2024 — Initial build

### Greedy heuristic instead of OR-Tools CP-SAT
**Decision:** Use a greedy nearest-available-berth + crane assignment algorithm for v1.
**Reason:** OR-Tools requires a separate install and CP-SAT formulation time exceeds the sprint budget. The greedy approach always terminates, is deterministic, and is easy to explain to judges.
**Greedy ceiling note:** Under a full-port burst scenario (112/124 slots CRITICAL, all berths affected), the greedy rerouter cannot improve average wait vs naive — it can only redistribute who waits, not reduce total queue time; test tolerance set to ≤3% regression, with CP-SAT noted as the only path to true average improvement.
**Next step:** CP-SAT is the documented v2 upgrade path (see `docs/architecture.md`).

### Queue-length forecasting instead of ML model
**Decision:** Use a rule-based queue-length scorer for congestion prediction (counts arrivals vs capacity per 2h slot).
**Reason:** Under the time budget a simple explainable model that visibly works beats a deep-learning model that requires training data, GPU, and tuning. Judges can understand the scoring logic in 30 seconds.
**Next step:** A gradient-boosted regressor (XGBoost) trained on historical port throughput data would be the v2 ML upgrade.

### In-memory state instead of database
**Decision:** API state is held in a Python dict between calls; no persistent database.
**Reason:** No multi-user / multi-session requirement in the prototype. Eliminating the DB removes setup complexity and a potential point of failure during the live demo.
**Next step:** PostgreSQL for multi-session history if productionized.

### Synthetic data only
**Decision:** All vessel/port data is generated by `src/simulation/generator.py`.
**Reason:** No real AIS feed or port operator data was available within the hackathon scope. The synthetic generator is seeded and reproducible, so demo results are deterministic.
**Documented in:** `docs/assumptions.md`.

### Pre-baked demo fallback
**Decision:** `demo/scenario_congested.json` is generated on first `/demo/scenario` call and cached to disk.
**Reason:** Live computation may be slow or flaky during judging. The pre-baked scenario guarantees a consistent, fast-loading demo.

### Return all_slots from /pipeline (not just flagged)
**Decision:** `/pipeline` and `/pipeline/inject` return the full 288-slot list (`all_slots`) alongside `flagged_slots`.
**Reason:** The heatmap was only receiving `flagged_slots` (HIGH/CRITICAL tier), meaning every populated cell was already orange/red. Without `all_slots`, there was literally no data to render green cells. Returning all slots allows the heatmap to show genuine low-risk (green) slots, moderate (yellow), and critical (red) — the full story.

### Per-berth independent busy tracker in predictor
**Decision:** Replaced the shared `berth_busy` dict (declared outside the berth loop) with a per-berth scalar `berth_busy_slot` reset at the start of each berth's pass.
**Reason:** The shared dict caused cross-contamination — when scoring B02, the tracker already reflected B01's vessel bookings from earlier in the outer loop, producing spurious `local_pressure=0.20` on every arrival slot regardless of actual load. This created a bimodal score cluster at 0.245 (everyone) and 0.74 (busy+normal). Independent trackers give each berth a clean slate.

### Risk score zero when no arrivals (occupancy ≠ congestion)
**Decision:** Slots with `n_arriving == 0` always score 0.0, even if the berth is occupied serving a prior vessel.
**Reason:** A berth running at capacity on an existing vessel is doing its job — it is not a congestion risk. Congestion risk only exists when additional vessels arrive and find limited capacity. The old code returned `carryover_frac * 0.20` for zero-arrival busy slots, filling 50% of heatmap cells with an artificial 0.20 score.

### Reroute diff filtered to ≥2h wait-delta threshold
**Decision:** In `inject_pipeline`, the `rerouted_vessels` list only includes vessels where `abs(wait_after - wait_before) >= 2.0 hours`.
**Reason:** Injecting one VLARGE vessel causes the greedy optimizer to naturally reassign 30–50% of all existing vessels to different berths — not because they are genuinely disrupted, but because the greedy sort order shifts. Most of these reassignments change wait time by <1h (trivial artefacts). The 2h threshold shows only meaningful reroutes.
