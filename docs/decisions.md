## 2024 — Initial build

### Greedy heuristic instead of OR-Tools CP-SAT
**Decision:** Use a greedy nearest-available-berth + crane assignment algorithm for v1.
**Reason:** OR-Tools requires a separate install and CP-SAT formulation time exceeds the sprint budget. The greedy approach always terminates, is deterministic, and is easy to explain to judges.
**Greedy ceiling note:** Under a full-port burst scenario (112/124 slots CRITICAL, all berths affected), the greedy rerouter cannot improve average wait vs naive — it can only redistribute who waits, not reduce total queue time; test tolerance set to ≤3% regression, with CP-SAT noted as the only path to true average improvement.
**Next step:** CP-SAT is the documented v2 upgrade path (see `docs/architecture.md`).

### Queue-length forecasting instead of ML model
**Decision:** Use a rule-based queue-length scorer for congestion prediction (counts arrivals vs capacity per 2h slot).
**Reason:** Under the time budget a simple explainable model that visibly works beats a deep-learning model that requires training data, GPU, and tuning. Judges can understand the scoring logic in 30 seconds.
**Next step:** A gradient-boosted regressor (XGBoost) trained on historical port throughput data would be the v2 ML upgrade.

### In-memory state instead of database
**Decision:** API state is held in a Python dict between calls; no persistent database.
**Reason:** No multi-user / multi-session requirement in the prototype. Eliminating the DB removes setup complexity and a potential point of failure during the live demo.
**Next step:** PostgreSQL for multi-session history if productionized.

### Synthetic data only
**Decision:** All vessel/port data is generated by `src/simulation/generator.py`.
**Reason:** No real AIS feed or port operator data was available within the hackathon scope. The synthetic generator is seeded and reproducible, so demo results are deterministic.
**Documented in:** `docs/assumptions.md`.

### Pre-baked demo fallback
**Decision:** `demo/scenario_congested.json` is generated on first `/demo/scenario` call and cached to disk.
**Reason:** Live computation may be slow or flaky during judging. The pre-baked scenario guarantees a consistent, fast-loading demo.
